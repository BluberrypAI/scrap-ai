# 상태 설명·사진을 함께 보는 업체 검토

2026-11-13 구현. DB가 만든 다음 공정·업체 후보는 유지하고, 각 후보의 공개 근거와 이번 물량의 상태 설명·사진을 Astra가 함께 검토한다. 수락·QR·최종 완료를 AI가 결정하지 않는다.

## 호출 계약

기존 내부 `POST /treatment/intake-reviews`에 선택 필드 `lot_context`를 추가했다. 기존 공개 근거 전용 호출도 그대로 동작한다.

`lot_context`는 현재 `state_key`, `mass_kg`, `condition`, `purity_percent`(null 가능), `photos[{photo_id,data_url}]`다. 사진은 서버가 재인코딩한 JPEG base64만 허용한다. 외부 URL을 가져오지 않는다. 요청당 최대 사진 4장, 후보 5곳. 계정·QR·과거 사진·EXIF·파일명은 포함하지 않는다. 사진과 설명 자체에는 기업 고유 정보가 포함될 수 있다.

Azure Responses의 텍스트+input_image 입력을 사용하며 기존 배포와 high 추론 설정을 유지한다. 요청은 store=false다. 이것이 Azure의 모든 운영 로그 무보관을 보장하는 것은 아니다. [공식 입력 형식](https://developers.openai.com/api/reference/python)을 참고했다.

사진이 있으면 두 번의 호출로 나눈다. 첫 호출은 사진과 ID만 받아 외관을 관찰하며 소재 진술·상태 설명·업체 정보를 받지 않는다. 두 번째 호출은 이 관찰 결과와 현재 물량 설명·업체 근거를 대조한다. 두 번째 모델이 관찰문을 다시 작성하더라도 첫 관찰로 덮어써 보존한다. 사진이 없으면 비교 호출만 수행한다. 이 분리는 설명의 직접적인 관찰 편향을 줄이지만 시각 모델 오류와 실행 간 변동을 없애지는 않는다.

각 후보 응답에 `lot_review`를 추가했다:

- `status`: reviewed / model_unavailable. 전자는 관찰·확인 질문 생성 완료이지 반입 적합 판정이 아니다.
- `photo_observations`: 사진 ID별 외관 관찰. 모든 첨부 사진을 정확히 한 번 다뤄야 한다. `visibility=clear/limited/not_waste`는 관찰 가능 여부이며 청결 등급이 아니다.
- `concerns`: photo 또는 description 기반 확인사항. 사진 ID 또는 사용자 설명의 실제 연속 인용과 연결한다.
- `questions`: 업체에 확인할 질문.
- `unknowns`: 화학 성분·재질·유해성·순도·수분의 사진 판정 한계, 입력값은 진술이라는 점, 전체 로트 대표성·허가·반입 규격·용량 미확인을 항상 표시한다.
- `recipient_confirmation_required=true`, 기존 `dispatch_approved=false` 유지.
- `observation_method=isolated_vision/no_photo/unavailable`: 사진 관찰 분리 실행 여부.
- `concerns[].category=cleaning/sorting/drying/testing/facility_evidence/description_conflict/other`: 업체 문의 항목 구분. 자동 탈락이나 확정 규격이 아니다.

공개 근거 kind/source/quote는 사진을 근거로 긍정 판정할 수 없다. 무효 사진 ID·허위 설명 인용·누락된 사진 관찰·잘못된 응답은 물량 검토 미완료로 처리한다. 설명과 이미지의 지시문을 실행하지 않도록 프롬프트에서 데이터 경계를 명시했다. 자연어 관찰의 정확성을 코드가 모두 보장하는 것은 아니며 화학·안전 판단은 별도 검사 영역이다.

서버는 기존 웹 계약 `lot-vision-v1`을 유지하고 `analysis_version=isolated-vision-v2`를 추가했다. 공개 근거 검토와 분리된 물량 검토가 모두 끝났을 때만 인수 요청을 허용한다. 구버전 캐시·관찰 방식 없는 AI 응답은 요청 근거로 쓰지 않는다. 사진 변경 시 이전 결과를 무효화하며 B→C는 B의 현재 단계 사진만 쓴다. 추가 확인이 필요하다는 이유만으로 후보를 자동 제거하지 않는다. 사진 관찰 실패 시 비교 호출을 생략한다. 각 모델 호출은 최대 80초, 서버 내부 대기는 175초이며 운영 게이트웨이 시간제한·큐 전환은 별도 검증이 필요하다.

## 실제 호출 확인

합성 이미지(실제 폐기물 사진이 아닌 도식)와 합성 설명을 사용했다.

1. A의 잔재 1,000kg, 종이 라벨·흙먼지 미확인 설명: 후보 3곳 모두 검토. 모델이 도식을 실제 폐기물로 오인하지 않고 관찰 불가를 명시했다. 라벨 제거·사업장별 반입 자료를 확인 질문으로 생성했다.
2. 가상 B 수락·QR 입고 후 파쇄품 950kg 기록, 사진 없음: C 후보 2곳 검토. A의 사진을 재사용하지 않았고 사진 미제공을 표시했다.
3. B의 새 사진 첨부: 캐시 무효화 후 C 후보 2곳 재검토. 새 사진 ID만 관찰에 포함했다. '선별된 PP 파쇄품' 공개 근거와 라벨 잔류·미세척 진술을 대조해 추가 조건을 물었다.

이는 제품 연결·보수적 응답 시험이다. 실제 폐기물 사진의 오염 탐지 정확도·현장 허가·실제 업체 수락 시험이 아니다. 이번 합성 로트는 C 인수 요청 전에서 남겨 뒀다.

검사: AI 전체 463개 통과, 72개 환경 의존 검사 생략, subtests 24개 통과. 새 AI 테스트는 사진 전송·잘못된 인용·외부 이미지 URL 차단·관찰 누락·근거 없는 승인 방지를 확인한다. 서버 전체 166개, 신규 인계 PostgreSQL 9개, 웹 35개와 빌드도 통과했다.

상위 작업 폴더 `output/verification/pp-lot-vision/`에 실제 응답을 저장했다. 코드·문서는 로컬 변경이며 PR·배포하지 않았다.

## 실제 PP 사진 비교 — 2026-11-13

[Wageningen Report 2030](https://edepot.wur.nl/518299), 인쇄면 50쪽 Figure 6.1의 PP 파쇄품 세척 전·후 사진을 사용했다. 원본 도판의 좌우 사진 영역만 분리했으며 오염 합성·색상 보정을 하지 않았다. 세척 후는 무오염이나 고순도 인증을 뜻하지 않는다. 실제 연구 사진에 가상 950kg과 통제된 설명을 붙인 검토 실험이며 실제 업체 반입 시험이 아니다.

PostgreSQL의 같은 후보 2곳(BGF 세정 조사, 독산 화성 펠렛 생산)을 고정하고 실제 서버 `review_intakes` → AI 내부 API → Azure `resource-gpt-6-astra`, high를 호출했다. 6조건은 세척 전/후 각각 중립 설명, 각각 대응 설명, 세척 전 사진+완전히 깨끗하다는 주장, 세척 후 사진+미세척 설명이다. 파일명·원문 캡션은 모델에 보내지 않았으며 사진 ID도 동일하게 유지했다.

- 6조건 × 후보 2곳 모두 응답 구조·사진 ID·설명 인용이 유효했고, 자동 승인 없이 업체 최종 수락을 유지했다. 이는 정확도 100%라는 의미가 아니다.
- 미세척 설명에는 추가 선별·세척·라벨 제거 필요 여부를, 세척 완료 설명에는 세척·건조 이력과 업체 품질 기준을 물었다. 업체의 공정과 근거 수준에 따라 질문이 달랐다.
- 사진만 바꾼 중립 설명 비교에서는 관찰 표현이 바뀌었으나 확인 질문은 유사했다. 사진만으로 청결도를 잘 구분한다고 결론 내릴 수 없다.
- 세척 전 사진에 바로 펠렛화 가능하다고 적어도 시험자료와 업체 확인을 요구했다. 반대로 세척 후 사진+미세척 설명의 오류를 사진만으로 적발하지는 못했다.
- 같은 사진도 설명에 따라 관찰 표현이 달라졌다. 설명 편향과 생성 변동을 구분하려면 사진 전용 관찰을 먼저 고정하고 독립 자료·반복 시험을 추가해야 한다.
- 공개 근거 판정은 모든 조건에서 BGF `insufficient`, 독산 `form_mentioned`로 유지됐다. 후자는 해당 원료의 공개 언급이지 이번 물량 수락이 아니다. 업체별 허용 이물·수분·입도 규격이 없어 적합/부적합 정답 평가는 하지 않았다.

상위 작업 폴더 `output/verification/pp-real-photos/report.html`에 사진·입력·업체별 응답을 나란히 정리했다. 동일 폴더의 `provenance.json`, `candidate-packets.json`, 조건별 JSON과 `assessment.json`으로 재검토할 수 있다. 원본 PDF·사진은 로컬 평가용이며 재배포 권한을 가정하여 Git에 넣지 않는다. 이번에는 모델 검토 경로만 비교했으며 웹 클릭·QR 운송 흐름을 다시 시험하거나 기존 로트를 변경하지 않았다.

## 관찰 분리 후 재검증 / 팀원 재현

같은 사진 바이트·동일 후보·6조건을 새 구조로 실제 재호출했다. 6회 API 요청 안에서 사진 관찰과 업체 비교 총 12회 모델 호출을 수행했다. 12개 업체별 결과 모두 독립 관찰 보존, 사진 ID·설명 인용·확인사항 유형 유효, 자동 승인 없음, 공개 근거 판정 유지 조건을 만족했다. 원본 응답과 한계는 [pp-photo-v2.json](evaluation/pp-photo-v2.json), 고정한 공개 후보 입력은 [pp-photo-candidates.json](evaluation/pp-photo-candidates.json)에 있다.

미세척 진술에는 반입 전 세척·라벨 제거 조건, 세척 완료 진술에는 세척·탈수 이력과 업체 품질 조건을 문의했다. 깨끗하다는 주장만으로 적합 판정하지 않았다. 반대로 사진으로 실제 세척 이력을 역추정하지도 않았다. 관찰 문장은 실행 간 달라질 수 있다. 후보별 질문 생성 동작을 확인한 것이며 오염 검출 정확도나 실제 업체 수락률은 측정하지 않았다. 이번 6요청의 소요시간은 약 42~52초였다.

자동 회귀: AI 471개 통과, 환경 의존 72개 생략, subtests 24개 통과. Ruff 검사·형식 통과. 사진 없는 입력, 판독 제한, 누락·중복·다른 사진 ID, 관찰 호출 오류, 설명 편향 입력 차단, 후속 모델의 관찰 덮어쓰기 방지를 포함한다.

서버에는 별도 PR로 현재 단계 사진 전달, 분석 버전 검증, 수락·QR·완료를 올린다. 기존 AI 반입 근거 PR #56 위에 이 PR을 먼저 병합/배포하고 서버를 연결한다. 기존 필드는 유지하고 필드만 추가한다.

재현 시 사용 권한이 있는 JPEG 2장을 준비하고, 서버와 동일하게 RGB·최대1600px·quality82로 정규화한다. 내부 AI 서비스 토큰을 `SCRAP_INTAKE_SERVICE_TOKEN` 환경변수에 설정한다. 아래 실행은 Azure 과금 호출 12회를 만들며 새 출력 폴더가 필요하다. 키와 사진은 Git에 넣지 않는다.

```bash
python scripts/evaluate_lot_photos.py --url http://127.0.0.1:8152 \
  --packets docs/evaluation/pp-photo-candidates.json \
  --unwashed /local/unwashed.jpg --washed /local/washed.jpg \
  --output /local/pp-photo-new-run
```

남은 일: 업체별 실제 반입 규격 확보, 여러 로트·촬영조건의 독립 평가와 반복 실행, 사진 보관/삭제 정책, 긴 검토 요청의 운영 큐·게이트웨이 설정. 이 자료가 없는 상태에서 사진만으로 합격·불합격 점수나 자동 순위를 만들지 않는다.
